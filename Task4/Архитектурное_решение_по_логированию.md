# Архитектурное решение по логированию

## Анализ системы

Система Александрит включает следующие компоненты из C4-диаграммы:

- Shop API (Java/SpringBoot) - прием заказов от B2C и B2B, загрузка 3d-файлов
- CRM API (Java/SpringBoot) - управление жизненным циклом заказа, взаимодействие с продавцами
- MES API (C#/ASP.NET) - управление производством, расчет стоимости изделий
- Shop DB (PostgreSQL) - хранение заказов и клиентских данных
- MES DB (PostgreSQL) - хранение производственных данных
- Messages Queue (RabbitMQ) - асинхронный обмен событиями между сервисами
- 3d files storage (S3) - хранение загруженных и сгенерированных моделей

Компоненты-источники логов отмечены на диаграмме цветом обводки элементов:

- Красная обводка (приоритет 1): MES API, CRM API
- Оранжевая обводка (приоритет 2): Shop API, Messages Queue (RabbitMQ)
- Желтая обводка (приоритет 3): Shop DB, MES DB (slow query log)

Диаграмма C4 с отмеченными источниками логов и новыми компонентами:
[jewerly_c4_logging.drawio](../Task4/jewerly_c4_logging.drawio)

Frontend-приложения (Internet Shop, CRM-фронт, MES-фронт) не включены в серверный сбор. Для них рекомендуется клиентский error tracking (например, Sentry) отдельным проектом.

## Список логов уровня INFO

Каждая запись содержит базовые поля: timestamp (ISO 8601, UTC), service, environment, level, trace_id, span_id, message. Поля trace_id и span_id пробрасываются из OpenTelemetry SDK, который внедряется в рамках задания по трейсингу (Task3) - одни и те же идентификаторы связывают лог и трейс конкретной операции.

Ниже - специфичные поля по каждому событию.

1. Создание заказа

   - order_id, user_id, source (web | api), channel (b2c | b2b)
   - сервис: Shop API
2. Изменение статуса заказа

   - order_id, user_id (или "system"), old_status, new_status
   - сервисы: Shop API, CRM API, MES API (в зависимости от статуса)
3. Публикация сообщения в RabbitMQ

   - order_id, topic, message_id
   - сервисы: CRM API, MES API
4. Получение сообщения из RabbitMQ

   - order_id, topic, message_id
   - сервисы: CRM API, MES API
5. Успешная обработка сообщения из RabbitMQ

   - order_id, topic, message_id, processing_duration_ms
   - сервисы: CRM API, MES API
6. Загрузка 3d-файла

   - order_id, user_id, file_size_bytes, file_type (upload | constructor)
   - сервис: Shop API
7. Запуск расчета стоимости

   - order_id, polygon_count
   - сервис: MES API
8. Завершение расчета стоимости

   - order_id, polygon_count, duration_ms, calculated_price
   - сервис: MES API
9. HTTP-запрос (access log)

   - method, path, status_code, duration_ms, user_id (если аутентифицирован)
   - сервисы: Shop API, CRM API, MES API
10. Назначение заказа на оператора

    - order_id, operator_id, assigned_by
    - сервис: MES API

## Использование других уровней логирования

DEBUG - только в dev-окружении. Вывод параметров SQL-запросов, тела HTTP-запросов и ответов, внутренних переходов конечного автомата заказа. В release и prod уровень не активен.

WARN - ситуации без сбоя, требующие внимания:

- повторная обработка одного message_id (дублирование в RabbitMQ)
- SQL-запрос выполнялся дольше 1 секунды
- попытка перевода заказа в недопустимый статус

ERROR - ошибки, прервавшие обработку:

- необработанное исключение в потребителе RabbitMQ
- ошибка записи в БД
- недоступность S3 при загрузке файла
- HTTP 5xx от внешнего сервиса

FATAL - только при невозможности запустить сервис: ошибка подключения к БД на старте, некорректная конфигурация.

## Мотивация

Текущая ситуация: разбор инцидентов происходит со слов клиентов. Разработчики тратят часы на поиск причины по косвенным признакам. При линейном росте нагрузки (+100 заказов в месяц) количество инцидентов растет пропорционально. После открытия B2B API ситуация ухудшилась: заказы от внешних систем создаются без участия оператора, и отследить путь конкретного заказа стало еще сложнее.

Три технических метрики, на которые повлияет внедрение логирования:

1. Среднее время диагностики инцидента - снижение с нескольких часов до 10-15 минут за счет поиска по trace_id и order_id в централизованном хранилище.
2. Процент инцидентов с установленной корневой причиной - рост с текущих 30% (разобрали со слов) до более 90% (нашли точный stack trace и цепочку событий).
3. Количество эскалаций от поддержки к разработчикам - снижение на 50-70%, так как поддержка сможет самостоятельно найти статус заказа и цепочку событий по order_id.

Две бизнес-метрики:

4. Время ответа клиенту на жалобу по заказу - снижение с нескольких дней до нескольких часов за счет быстрого нахождения order_id в логах.
5. Количество потерянных заказов в месяц - снижение благодаря алертингу на ошибки в RabbitMQ-потребителях и аномальный рост ошибочных статусов.

## Приоритет внедрения логирования и трейсинга

Команда не может реализовать одновременно логирование и трейсинг для всех систем. Порядок расставлен исходя из вклада каждой системы в проблему потерянных заказов и затрат на внедрение.

Первый этап - CRM API и MES API для обоих инструментов.

Для логирования это самые критичные системы, именно здесь происходят все статусные переходы заказа. Для трейсинга CRM API также идет первым. MES API в трейсинге идет вторым из-за сложности интеграции OpenTelemetry SDK при наличии одного C#-разработчика, но в логировании он идет параллельно с CRM API - добавление Serilog с выводом в stdout значительно проще, чем полная OTel-инструментация. Разрыв в порядке обусловлен разной трудоемкостью инструментов, а не разным пониманием приоритетов.

Второй этап - Shop API.

Точка входа для B2C и B2B, нужна для диагностики проблем на этапе создания заказа. В трейсинге Shop API идет первым, так как именно он создает корневой спан. Для логирования принципиального отличия нет - логи Shop API дополняют, но не замещают логи CRM API и MES API.

Третий этап - RabbitMQ, Shop DB, MES DB.

Инфраструктурный уровень, добавляется после того, как сервисы уже логируют события. Slow query log из PostgreSQL настраивается на уровне Managed Service без изменений в коде.

## Предлагаемое решение

Стек: Grafana Loki + Promtail + Grafana + AlertManager.

Grafana и AlertManager - это те же инстансы, которые развернуты в рамках задания по мониторингу (Prometheus + Grafana + AlertManager). Loki подключается к существующей Grafana как второй источник данных - отдельный UI не создается. Новые правила алертинга на основе логов добавляются к существующей конфигурации AlertManager.

Выбор Loki: команда уже использует Grafana, добавление Loki не требует нового UI и переобучения. Loki не индексирует содержимое логов - только метаданные (labels), что дает существенную экономию RAM по сравнению с ELK при умеренном объеме.

### Компоненты решения

Promtail (агент сбора) разворачивается на каждом EC2-инстансе. Читает stdout/stderr сервисов, добавляет labels (service, environment, instance), отправляет потоки в Loki по HTTP.

Loki (хранилище логов) разворачивается как отдельный инстанс в Yandex Cloud. Принимает потоки от всех агентов Promtail, хранит с индексацией по labels.

Grafana (UI) - существующий инстанс из задания по мониторингу. Loki добавляется как второй data source. Используется для поиска по LogQL, построения дашбордов и настройки алертов по логам.

AlertManager - существующий инстанс из задания по мониторингу. К нему добавляются новые правила алертинга на основе данных из Loki.

Новые компоненты и связи отражены на диаграмме C4 оранжевым цветом. Grafana и AlertManager показаны как расширенные (существующие из задания по мониторингу) компоненты.

### Изменения в сервисах

Shop API и CRM API (Java/SpringBoot):

- Добавить зависимость logstash-logback-encoder
- Настроить logback-spring.xml: вывод в stdout в формате JSON
- Добавить MDC-поля: trace_id, span_id, order_id, user_id (пробрасываются автоматически из OTel SDK через MDC bridge при наличии OpenTelemetry-инструментации)

MES API (C#/ASP.NET):

- Добавить NuGet-пакеты: Serilog.AspNetCore, Serilog.Formatting.Compact
- Настроить Program.cs: вывод в stdout в формате JSON
- Serilog и OpenTelemetry SDK (из задания по трейсингу) настраиваются независимо, конфликта нет

### Политика безопасности

Доступ к Grafana и данным логов - только через VPN или внутреннюю сеть Yandex Cloud. Аутентификация через встроенные учетные записи Grafana (при наличии корпоративного SSO - через него).

Роли:

- Developer: полный доступ к логам всех окружений
- Support: только чтение, только prod-потоки, поиск только по order_id и status

Чувствительные данные не пишутся в логи. Запрещенные поля: email, phone, full_name, payment_card_number, delivery_address. Поля order_id и user_id (UUID) допустимы - они не являются прямыми персональными данными. Список совпадает с аналогичным из задания по трейсингу и закрепляется в единой инструкции по разработке, проверяется на code review.

### Политика хранения

- prod: retention 30 дней, после - автоматическое удаление
- release: retention 14 дней
- dev: retention 7 дней

Отдельные потоки (streams) в Loki по каждому сервису:

- {service="shop-api", env="prod"}
- {service="crm-api", env="prod"}
- {service="mes-api", env="prod"}

Оценка объема: при текущей нагрузке (~1000 заказов/месяц, ~50 событий на заказ, средний размер JSON-записи ~500 байт) - около 25 MB/месяц несжатых бизнес-логов. С учетом access-логов и инфраструктурных событий - до 300-500 MB/месяц до сжатия. Loki применяет сжатие потоков, реальный размер на диске ниже в 5-10 раз.

## Анализ и алертинг

Алерты настраиваются в AlertManager (тот же инстанс, что используется для метрик из задания по мониторингу). К существующим правилам добавляются следующие:

1. Error rate в сервисах - более 10 записей уровня ERROR в MES API или CRM API за 5 минут. Уведомление DevOps и дежурного разработчика.
   LogQL: count_over_time({service=~"mes-api|crm-api"} | json | level="ERROR" [5m]) > 10
2. Ошибка в потребителе RabbitMQ - появление ERROR с контекстом очереди в любом из API-сервисов. Немедленный алерт, ручной разбор возможного потерянного заказа. Этот алерт дополняет метрику dead-letter-exchange из задания по мониторингу - разные уровни обнаружения одной проблемы.
3. Зависший заказ - отсутствие смены статуса для конкретного order_id дольше 60 минут после появления SUBMITTED. Автоматическое создание тикета. Дополняет аналогичный алерт из задания по трейсингу на основе SPM-метрик Jaeger - два независимых источника повышают надежность обнаружения.
4. Аномальный рост создания заказов - количество событий "создание заказа" выросло более чем в 5 раз по сравнению со средним за последний час. Алерт на возможный DDoS или ошибку в B2B-интеграции. Нужно искать аномалию: было 4 записи в минуту, стало 10 000 - это не органический рост, это либо атака, либо баг во внешней системе.
   LogQL: rate({service="shop-api"} | json | message="Order created" [5m]) > 5 * avg_over_time(rate({service="shop-api"} | json | message="Order created" [5m])[1h:5m])
5. Slow query в БД - запись в PostgreSQL slow query log со временем выполнения более 2 секунд. Добавляется в еженедельный отчет для разработчиков.

Выбор - Loki + Grafana. Ключевые аргументы: команда уже использует Grafana для мониторинга, добавление Loki не требует нового UI и переобучения. Полнотекстовый поиск не является приоритетом, так как все события структурированы в JSON и поиск идет по конкретным полям (order_id, status, user_id). Если в будущем потребуется полнотекстовый поиск по стек-трейсам - можно настроить выгрузку из Loki в OpenSearch для конкретных потоков, не меняя основную инфраструктуру.
