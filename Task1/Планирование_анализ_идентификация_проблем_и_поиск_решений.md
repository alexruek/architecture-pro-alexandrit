# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ системы

### 1.1. Текущий ландшафт

Система состоит из трех SPA-приложений с отдельными бекендами и двух баз данных. Компоненты взаимодействуют через RabbitMQ (асинхронно) и напрямую по HTTP (синхронно).

Ключевые потоки:

- Customer -> Internet Shop -> Shop API -> Shop DB / 3d files storage / Messages Queue
- Messages Queue -> CRM API -> Shop DB
- CRM -> CRM API -> Messages Queue
- Messages Queue -> MES API -> MES DB / 3d files storage
- API user -> MES API (публичный endpoint для расчета стоимости)
- Operator -> MES -> MES API -> MES DB

Разделяемые ресурсы (точки конкуренции):

- Shop DB: читают и пишут Shop API и CRM API одновременно
- Messages Queue: единственный брокер для всех межсервисных событий
- 3d files storage: используют Shop API, CRM API, MES API

Критический путь заказа:

```
INITIATED -> FILE_UPLOADED -> SUBMITTED
  -> [Messages Queue] -> MES API: PRICE_CALCULATED (2-30 мин, зависит от полигонов)
  -> [Messages Queue] -> CRM API: MANUFACTURING_APPROVED (ручное, время не ограничено)
  -> [Messages Queue] -> MES API: MANUFACTURING_STARTED (ручное, оператор берет заказ сам)
  -> MES API: MANUFACTURING_COMPLETED -> PACKAGING -> SHIPPED
  -> [Messages Queue] -> CRM API: CLOSED
```

Описанный критический путь содержит семь переходов через Messages Queue. Каждый из них - потенциальная точка потери заказа при отсутствии механизма повтора и мониторинга.

### 1.2. Инфраструктурный контекст

- Каждый сервис - один EC2-инстанс
- Каждая БД - один Managed-инстанс (читает и пишет один узел)
- Три окружения: dev, release, prod
- Деплой в prod и release - вручную
- CI/CD: только unit-тесты и ручное QA

## 2. Идентификация проблем

Как определяем степень важности проблемы:

1. Есть ли прямая связь с потерей заказов или денег прямо сейчас?
   Да - критическое
2. Блокирует ли работу пользователей или существенно деградирует систему?
   Да - высокое
3. Замедляет процессы, но не останавливает их?
   Да - среднее

2.1. Проблемы наблюдаемости

П-01: Отсутствует мониторинг инфраструктуры и сервисов.
Нет метрик по CPU, памяти, latency, error rate. Команда узнает о проблемах от клиентов, а не от системы.
Влияние высокое - без мониторинга время обнаружения инцидента измеряется часами - узнаем от клиентов, а не от системы.

П-02: Отсутствует централизованное логирование.
Разбор инцидентов требует ручного подключения к каждому EC2 и разбор локальных файлов. При нескольких сервисах это занимает часы.
Влияние высокое - при инциденте разработчик тратит 2-3 часа на ручной разбор по EC2 вместо 10 минут в едином интерфейсе - каждый инцидент обходится дороже.

П-03: Отсутствует распределенный трейсинг.
Невозможно восстановить полный путь конкретного заказа через Shop API -> RabbitMQ -> CRM API -> MES API. Нельзя определить, на каком шаге заказ завис или потерялся.
Влияние высокое - без трейсинга каждая жалоба на зависший заказ - ручное расследование с неопределенным результатом.

### 2.2. Проблемы надежности и потери заказов

П-04: Messages Queue не настроен с Dead Letter Exchange (DLX).
Если потребитель упадет во время обработки сообщения, сообщение будет потеряно или уйдет в бесконечную петлю retry без видимости. Это прямая причина "зависших" заказов.
Влияние критическое - прямая причина потери заказов и жалоб клиентов.

П-05: Нет механизма идемпотентной обработки сообщений из очереди.
При повторной доставке сообщения (at-least-once delivery в Messages Queue) потребитель может создать дубликат заказа или изменить статус повторно.
Влияние критическое - Messages Queue (RabbitMQ) гарантирует at-least-once доставку - повторная доставка сообщения без идемпотентности создает дубликат заказа или некорректный статус. При масштабировании вероятность повторов растет.

П-06: Отсутствует rate limiting на публичном MES API.
После открытия B2B API система была перегружена входящими заказами. Нет механизма ограничения потока от внешних клиентов.
Влияние критическое - компания уже потеряла несколько крупных контрактов из-за перегрузки после открытия публичного API. Проблема уже реализовалась.

П-07: Расчет стоимости занимает до 30 минут.
Нет механизма уведомления клиента о прогрессе. Нет таймаута или очереди задач с приоритетами. При падении MES во время расчета результат теряется.
Влияние критическое - при расчете длиной 30 минут и единственном инстансе MES API вероятность падения в этом окне ненулевая. Нет retry - значит заказ теряется гарантированно при любом сбое во время расчета.

### 2.3. Проблемы производительности

П-08: Медленная загрузка дашборда заказов в MES. Каждый оператор при входе выполняет тяжелый запрос к единственному инстансу MES DB. Пагинация и фильтр не решили проблему - корень в отсутствии серверного кеша. Одни и те же данные запрашиваются каждым оператором независимо.
Влияние высокое - медленная загрузка, значит оператор видит новый заказ позже конкурента внутри команды. При росте числа заказов проблема линейно возрастает.

П-09: Единственный инстанс каждой БД без разделения чтения и записи. Shop DB используют Shop API и CRM API одновременно. MES DB обслуживает и операторов (чтение дашборда), и запись статусов заказов. Нет read replica. При росте нагрузки операции чтения и записи конкурируют за один узел.
Влияние высокое - нагрузка растет на 100 заказов в месяц - это предсказуемое исчерпание ресурсов БД на горизонте 3-6 месяцев без изменений.

П-10: Единственный инстанс каждого сервиса (SPOF).
При падении Shop API, CRM API или MES API сервис полностью недоступен. Нет горизонтального масштабирования.
Влияние высокое - при падении любого сервиса весь поток заказов останавливается.

### 2.4. Проблемы процессов разработки и доставки

П-11: CI/CD покрывает только unit-тесты, QA - ручное.
Задержки релиза достигают месяца и больше. QA-инженер хочет автоматизации, но нет инструментария. Это замедляет доставку любых исправлений.
Влияние среднее - замедляет доставку исправлений, но не влияет на текущие заказы напрямую.

| Проблема                     | Влияние         | Аргументация                                                                   |
| ------------------------------------ | ---------------------- | ------------------------------------------------------------------------------------------ |
| П-04 DLX                            | критическое | прямая потеря заказов, подтверждена жалобами        |
| П-05 идемпотентность | критическое | дубликаты заказов при повторной доставке               |
| П-06 rate limiting                  | критическое | уже привела к потере контрактов                                 |

## 3. Инициативы

### 3.1. Полный список инициатив

И-01: Внедрить мониторинг (Prometheus + Grafana).
Установить экспортеры на все EC2, добавить метрики в Java (Micrometer) и C# (OpenTelemetry). Настроить дашборды и AlertManager.

И-02: Внедрить централизованное логирование (Loki + Promtail + Grafana).
Настроить структурированные JSON-логи в Java (Logback) и C# (Serilog). Promtail собирает и отправляет в Loki. Grafana - единый интерфейс для логов и метрик.

И-03: Внедрить распределенный трейсинг (OpenTelemetry + Jaeger).
Добавить OTel SDK в Shop API, CRM API, MES API. Пропагировать trace context через RabbitMQ headers (W3C TraceContext). Развернуть OTel Collector + Jaeger.

И-04: Настроить Dead Letter Exchange в RabbitMQ.
Для каждого топика настроить DLX и отдельную dead-letter-queue. Добавить мониторинг количества сообщений в DLQ. Настроить алерт при появлении первого сообщения в DLQ.

И-05: Добавить Redis-кеш для дашборда заказов в MES.
Кешировать списки заказов по статусу. Паттерн Cache-Aside. Инвалидация по ключу при изменении статуса. TTL как страховочный механизм.

И-06: Добавить read replica для MES DB.
Направить все SELECT-запросы оперативного дашборда на реплику. Снизить нагрузку на основной узел, который используется для записи.

И-07: Добавить rate limiting на MES API.
Ограничить количество запросов по API-ключу для B2B клиентов. Вернуть HTTP 429 при превышении лимита с заголовком Retry-After.

И-08: Сделать расчет стоимости полностью асинхронным с уведомлением.
Добавить webhook или polling endpoint для B2B клиентов. Для веб-клиентов - websocket или SSE для получения результата расчета. Добавить очередь задач с приоритетами (срочные vs обычные заказы).

И-09: Автоматизировать E2E-тесты.
Внедрить Playwright или Cypress для автоматизации критических сценариев: создание заказа, загрузка файла, смена статуса. Подключить к CI/CD.

И-10: Добавить идемпотентную обработку сообщений.
Хранить идентификаторы уже обработанных сообщений (message_id) в БД или Redis. Перед обработкой проверять, не было ли это сообщение уже обработано.

И-11: Добавить возможность горизонтального масштабирования.
Вынести конфигурацию сервисов во внешние переменные окружения. Убедиться, что сервисы stateless. Подготовить к деплою нескольких инстансов за балансировщиком нагрузки.

## 4. Приоритизация инициатив

### 4.1. Принцип расстановки приоритетов

Критерии оценки:

- Impact: насколько сильно решает текущие проблемы бизнеса (потери заказов, жалобы клиентов)
- Effort: сколько времени и ресурсов команды требует реализация

Первоочередные задачи - это задачи, которые дают видимость и контроль над системой, либо останавливают потерю заказов с минимальными затратами.

### 4.2. Матрица приоритетов


| ID    | Инициатива                                        | Impact         | Effort         | Приоритет |
| ----- | ----------------------------------------------------------- | -------------- | -------------- | ------------------ |
| И-04 | Dead Letter Exchange                                        | Высокий | Низкий   | 1                  |
| И-07 | Rate limiting                                               | Высокий | Низкий   | 2                  |
| И-01 | Мониторинг                                        | Высокий | Средний | 3                  |
| И-05 | Redis-кеш для MES                                     | Высокий | Средний | 4                  |
| И-02 | Логирование                                      | Высокий | Средний | 5                  |
| И-03 | Трейсинг                                            | Высокий | Средний | 6                  |
| И-10 | Идемпотентность сообщений           | Средний | Средний | 7                  |
| И-06 | Read replica MES DB                                         | Средний | Средний | 8                  |
| И-09 | E2E автотесты                                      | Средний | Средний | 9                  |
| И-08 | Асинхронный расчет                         | Высокий | Высокий | 10                 |
| И-11 | Горизонтальное масштабирование | Средний | Высокий | 11                 |

Наблюдаемость внедряется в порядке: мониторинг - логирование - трейсинг.
Мониторинг дает агрегированную картину состояния системы и алерты - это нужно немедленно. Логирование закрывает разбор инцидентов внутри каждого сервиса. Трейсинг строится поверх обоих и связывает картину между сервисами - его ценность максимальна когда метрики и логи уже есть.

### 4.3. Обоснование приоритетов

И-04 - первый приоритет. DLX в RabbitMQ - это конфигурация брокера, не требующая изменений в коде приложений. При этом она напрямую решает проблему потери сообщений и "зависших" заказов. Единственное изменение кода - добавить параметр при объявлении очереди и создать dead-letter-queue. В итоге потерянные сообщения попадают в отдельную очередь, откуда их можно повторно обработать или проанализировать.

И-07 - второй приоритет. Важная задача с низкими затратами на реализацию. Rate limiting остановит перегрузку системы со стороны B2B клиентов и предотвратит повторение ситуации с "завалом заказов".

И-01 - третий приоритет. Без мониторинга невозможно объективно измерить эффект от любого другого улучшения. Сейчас о проблемах узнают от клиентов, а не от системы. Prometheus + Grafana - стандартное решение . Установка node_exporter и postgres_exporter не требует изменений в коде сервисов.

И-05 - четвертый приоритет. Жалобы операторов на медленный MES - прямое влияние на производительность производства. Redis Cache-Aside на список заказов по статусу - локальное изменение в MES API (C#), не затрагивающее другие сервисы. Снизит нагрузку на MES DB и ускорит загрузку дашборда.

И-03 и И-02 (трейсинг и логирование) - идут вместе как единый блок наблюдаемости. Они требуют изменений в коде всех трех бекендов, поэтому затраты на реализацию выше, но они необходимы для системного понимания проблем.

### 4.4. Три инициативы при ограниченном ресурсе

Если команда может реализовать только три пункта за полгода:

1. И-04 + И-07
   Минимальные затраты на реализацию, максимальный impact. Останавливает потерю заказов здесь и сейчас. Это технический долг, который не требует найма новых специалистов и занимает несколько дней.
2. Блок наблюдаемости (И-01 + И-02 + И-03 как одна инициатива)
   Без мониторинга, логирования и трейсинга невозможно подтвердить, что другие улучшения работают. Этот блок дает команде инструменты для диагностики и доказательства прогресса бизнесу.
3. И-05 (Redis-кеш для MES)
   Жалобы операторов влияют на производственные показатели. Кеш - локальное изменение с быстрым эффектом.

Выбор обоснован тем, что первые две инициативы устраняют первопричины потерь заказов и дают видимость, а третья снимает самую ощутимую жалобу внутренних пользователей.

## 5. Целевая архитектура через полгода

### 5.1. Что добавится к текущей архитектуре

Инфраструктура наблюдаемости:

- Prometheus (сбор метрик) + Grafana (дашборды и алерты)
- Loki + Promtail (логирование)
- OpenTelemetry Collector + Jaeger (трейсинг)
- AlertManager (уведомления в мессенджер команды)

Надежность:

- Dead Letter Exchange для каждой очереди RabbitMQ
- Rate limiting на MES API (api-gateway или middleware в MES API)
- Redis-кеш для MES (список заказов по статусам)

Производительность:

- Read replica для MES DB

Процессы:

- Автоматизированные E2E-тесты для критических сценариев заказа

Подготовительные работы:

* Вынести конфигурацию всех сервисов в переменные окружения
* Убедиться в stateless-природе Shop API, CRM API, MES API
* Это не дает эффекта сейчас, но открывает горизонтальное масштабирование без переработки архитектуры в следующем периоде

### 5.2. Что остается без изменений

- Технологический стек сервисов (Vue, SpringBoot, C#, React)
- Инфраструктура Yandex Cloud (EC2, Managed PostgreSQL, S3)
- Модель данных и бизнес-логика
- Горизонтальное масштабирование - не в приоритете первого полугодия, но сервисы должны быть подготовлены (stateless, конфигурация через env)

### 5.3. Открытые вопросы для следующего периода

Следующие направления не включены в полугодовой план из-за высоких затрат на реализацию или зависимости от результатов текущих инициатив:

- Переход на Kubernetes (упоминается DevOps-инженером как направление)
- Разделение Shop DB и CRM DB (сейчас обе системы работают с одной БД)
- Асинхронный расчет стоимости с webhook-уведомлением для B2B
- Горизонтальное масштабирование Shop API при дальнейшем росте B2C трафика

## 6. Контекст для найма

При реализации блока наблюдаемости (мониторинг + логирование + трейсинг) текущий DevOps-инженер будет перегружен. Если Kubernetes планируется в следующем полугодии, стоит рассмотреть найм второго DevOps-инженера с опытом в Kubernetes и Helm. Это обоснование для бизнеса: без DevOps-поддержки либо откладываются инфраструктурные улучшения, либо разработчики тратят время на инфраструктуру вместо фич.

QA-инженер хочет заниматься автоматизацией. Это хорошая возможность внедрить E2E-тесты без найма отдельного QA-автоматизатора, но ему нужно выделить время и обучение (Playwright/Cypress).
