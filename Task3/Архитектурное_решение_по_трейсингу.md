# Архитектурное решение по трейсингу

## Анализ системы

Заказ в системе Александрит проходит через несколько сервисов и брокер сообщений. На каждом переходе есть риск потери или зависания.

Компоненты, которые необходимо покрыть трейсингом (выделены на диаграмме красным):

- Shop API - принимает заказ от клиента, загружает 3d-файл в S3, публикует сообщение в RabbitMQ.
- CRM API - потребляет сообщения из RabbitMQ, изменяет статус заказа, публикует ответ в очередь.
- MES API - потребляет сообщения из RabbitMQ, запускает расчет стоимости, обновляет статус в MES DB.
- RabbitMQ - каждый переход через очередь является потенциальным местом разрыва трейса.

Места, где заказ может потеряться или зависнуть:

1. Shop API -> RabbitMQ: сообщение о новом заказе не попало в очередь при кратковременной недоступности брокера.
2. RabbitMQ -> CRM API: потребитель упал в процессе обработки сообщения до записи нового статуса в базу.
3. CRM API -> RabbitMQ: сообщение о подтверждении заказа (MANUFACTURING_APPROVED) не опубликовано.
4. RabbitMQ -> MES API: то же самое при получении сообщений о подтвержденных заказах.
5. MES API -> расчет стоимости: процесс занимает от 2 до 30 минут, видимости промежуточного состояния нет.
6. MES API -> S3: ошибка при сохранении или чтении 3d-файла не отслеживается системно.

Данные, которые должны попадать в каждый спан:

- trace_id - сквозной идентификатор цепочки вызовов через все сервисы
- span_id, parent_span_id - структура иерархии спанов
- service.name - имя сервиса (shop-api, crm-api, mes-api)
- span.name - имя операции (create-order, publish-message, consume-message, calculate-price)
- order.id - бизнес-идентификатор заказа (UUID, не является персональными данными)
- order.status - статус заказа на момент операции
- user.id - идентификатор пользователя или внешней B2B-системы (UUID)
- messaging.system - значение «rabbitmq» при передаче через очередь
- messaging.destination - имя топика RabbitMQ
- http.method, http.route, http.status_code - для HTTP-взаимодействий между сервисами
- error - признак ошибки и текст исключения при наличии

Персональные данные (имя клиента, email, адрес доставки, платежная информация) в трейсы не попадают.

## Мотивация

Сейчас разбор инцидента с конкретным заказом занимает часы. Нужно вручную сопоставить записи из трех баз данных и восстановить цепочку событий. Нередко корневую причину потери заказа так и не удается установить, команда работает со слов клиента. После открытия B2B API ситуация ухудшилась. Заказы от внешних систем создаются без участия оператора, и отследить путь конкретного заказа по журналам трех разных систем стало еще сложнее.

Трейсинг решает эту проблему за счет сквозного trace_id, который связывает все шаги обработки заказа в единую цепочку, независимо от того, через какой сервис и очередь прошло сообщение.

Технические метрики, на которые повлияет внедрение трейсинга:

1. Время на локализацию проблемы с конкретным заказом - снижение с нескольких часов до нескольких минут за счет единого интерфейса поиска по trace_id или order_id.
2. Время обработки каждого статусного перехода - появится возможность отслеживать p50, p95, p99 по каждому шагу и выявлять деградацию до момента, когда клиент начнет жаловаться.
3. Процент ошибочных спанов по сервису - метрика error rate, которой сейчас нет ни в одном из трех сервисов.
4. Количество заказов с разрывом трейса на границе RabbitMQ - прямой индикатор потерянных сообщений.

Бизнес-метрики:

5. Среднее время от статуса SUBMITTED до MANUFACTURING_APPROVED - позволит подтвердить или опровергнуть гипотезы о причинах задержек и даст инструмент для разговора с клиентами, потерявшими заказ.
6. Сокращение времени закрытия тикетов саппорта по потерянным заказам - меньше эскалаций к разработчикам, меньше ручного разбора в трех разных базах данных.

## Предлагаемое решение

### Технологии

Инструментация сервисов выполняется через OpenTelemetry SDK. Это открытый стандарт CNCF, не привязанный к конкретному бэкенду. При необходимости сменить систему хранения можно без изменений в коде сервисов.

Для хранения и визуализации трейсов используется Jaeger. Поддерживает экспорт метрик в Prometheus через механизм SPM (Service Performance Monitoring), что позволяет строить алерты на основе данных трейсинга без дополнительного кода.

Между сервисами и Jaeger устанавливается OpenTelemetry Collector. Он принимает трейсы от всех сервисов по протоколу OTLP gRPC, применяет фильтрацию и семплирование, маршрутизирует данные в Jaeger. Такая архитектура позволяет добавить несколько бэкендов или поменять стратегию семплирования без правок в коде сервисов.

### Доработки по сервисам

Shop API (Java, Spring Boot):

- Добавить зависимость opentelemetry-spring-boot-starter.
- Настроить экспорт в OTel Collector через OTLP gRPC (endpoint: otel-collector:4317).
- HTTP-заголовки W3C TraceContext пробрасываются автоматически через RestTemplate/WebClient instrumentation.
- При публикации в RabbitMQ - добавлять trace context в заголовки сообщения через opentelemetry-instrumentation-spring-rabbitmq.

CRM API (Java, Spring Boot):

- Те же зависимости, что и для Shop API.
- При получении сообщения из RabbitMQ - trace context извлекается из заголовков, создается дочерний спан с тем же trace_id.

MES API (C#, ASP.NET Core):

- Добавить NuGet-пакеты: OpenTelemetry.Extensions.Hosting, OpenTelemetry.Instrumentation.AspNetCore, OpenTelemetry.Exporter.OpenTelemetryProtocol.
- Настроить экспорт трейсов в OTel Collector через OTLP gRPC (endpoint: otel-collector:4317).
- В MES API регистрируются два экспортера параллельно: OpenTelemetry.Exporter.Prometheus.AspNetCore для метрик (в рамках задания по мониторингу) и OpenTelemetry.Exporter.OpenTelemetryProtocol для трейсов (в рамках данного задания). Оба экспортера настраиваются через один вызов AddOpenTelemetry() в Program.cs и не конфликтуют.
- Для RabbitMQ - добавить ручную реализацию propagation через TextMapPropagator при публикации и потреблении сообщений.

### Новые компоненты и связи

Новые компоненты (выделены красным):

- OTel Collector - принимает трейсы от всех трех API-сервисов по OTLP gRPC, маршрутизирует в Jaeger.
- Jaeger - хранит и визуализирует трейсы, предоставляет поиск по trace_id и order_id через UI.

Новые связи (красные):

- Shop API -> OTel Collector (OTLP gRPC, порт 4317)
- CRM API -> OTel Collector (OTLP gRPC, порт 4317)
- MES API -> OTel Collector (OTLP gRPC, порт 4317)
- OTel Collector -> Jaeger (OTLP gRPC)

### Автоматический мониторинг и алертинг на основе трейсинга

Jaeger поддерживает экспорт метрик производительности сервисов через SPM endpoint в Prometheus. Это позволяет строить алерты непосредственно на данных трейсинга без дополнительных инструментов сбора метрик.

Prometheus и AlertManager разворачиваются в рамках задания по мониторингу - это одни и те же инстансы. В контексте трейсинга к существующему Prometheus добавляется новый scrape job для сбора SPM-метрик из Jaeger, к AlertManager добавляются новые правила алертинга по данным трейсов. Отдельные инстансы не требуются.

Новые связи (выделены зеленым):

- Jaeger -> Prometheus (новый scrape job для SPM-метрик)
- Prometheus -> AlertManager (новые правила алертинга на основе данных трейсинга)

Новые правила алертинга:

- Заказ в статусе SUBMITTED без перехода в PRICE_CALCULATED дольше 40 минут - уведомление в канал саппорта. Источник: SPM-метрика длительности спана create-order в Shop API.
- Latency p95 для операции consume-message в MES API превысил 35 минут - предупреждение о деградации расчетного движка. Источник: SPM-метрика по имени спана.
- Разрыв трейса на границе RabbitMQ: у producer-спана нет дочерних consumer-спанов через 15 минут после публикации. Источник: отсутствие дочерних спанов с тем же trace_id.
- Процент ошибочных спанов для CRM API или MES API превысил 5% за последние 5 минут. Источник: SPM error rate по конкретной операции - дополняет аналогичный алерт на HTTP 500 из задания по мониторингу, поскольку позволяет изолировать ошибку до уровня конкретного спана, а не только HTTP-ответа.

## Компромиссы

MES API написан на C# - в команде один C#-разработчик и тимлид. Разработка займет больше времени, чем для Java-сервисов. На первом этапе трейсинг внедряется в Shop API и CRM API, MES API - во второй очереди. При таком порядке трейс будет обрываться перед MES, но это лучше, чем полное отсутствие видимости.

Пробрасывание context через RabbitMQ требует одновременных изменений на стороне producer и consumer. При частичном внедрении трейс обрывается на границе очереди. Нужно явно задокументировать это ограничение для команды поддержки, чтобы не создавать ложных ожиданий.

Хранение трейсов требует дискового пространства. По умолчанию Jaeger хранит все спаны в памяти (in-memory storage). Для production необходимо настроить внешнее хранилище - Cassandra или Elasticsearch - это дополнительный инфраструктурный компонент, требующий поддержки DevOps.

Расчет стоимости занимает до 30 минут. Стандартный timeout для трейса в Jaeger может не охватывать такую длительность без дополнительной настройки max-trace-duration. Нужно проверить, что длинные спаны корректно записываются и не обрезаются.

OTel SDK добавляет около 1-3 мс к времени ответа каждого запроса. При текущей нагрузке это несущественно.

Семплирование по умолчанию - 100% трейсов. При значительном росте нагрузки потребуется настройка вероятностного или rate-based семплирования через OTel Collector, иначе объем хранимых данных будет расти пропорционально числу заказов.

## Безопасность

Jaeger UI доступен только внутри корпоративной сети или через VPN. Внешний доступ закрывается на уровне security group в Yandex Cloud - входящий трафик на порт 16686 разрешен только с IP-адресов корпоративной VPN.

Аутентификация в Jaeger реализуется через обратный прокси (nginx) с интеграцией с корпоративным SSO. На первом этапе - basic auth. Вход в систему доступен только сотрудникам с активной учетной записью и ролью «Developer» или «Support».

В трейсах не должны появляться персональные данные. В коде сервисов запрещается добавлять в атрибуты спанов: имя клиента, email, номер телефона, адрес доставки, данные платежной карты. Логируются только order_id, user_id (UUID), статусы заказа, технические параметры (polygon_count, calculated_price). Требование закрепляется в инструкции по разработке и проверяется на code review.

Передача данных от сервисов до OTel Collector происходит внутри VPC - TLS на этом участке необязателен. Если OTel Collector будет вынесен за пределы VPC, TLS настраивается обязательно.

Доступ к данным трейсинга предоставляется по ролям:

- Developer - полный доступ к Jaeger UI, поиск по любым атрибутам.
- Support - только поиск по order_id и просмотр статусных переходов.

Разграничение реализуется через группы в корпоративном SSO.
