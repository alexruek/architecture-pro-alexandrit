# Выбор и настройка мониторинга в системе

## Краткое описание

Система "Александрит" обрабатывает заказы через цепочку из нескольких сервисов, связанных через брокер сообщений. Сейчас нет инструментов, которые позволяют наблюдать за состоянием системы изнутри. Это создает конкретные проблемы:

1. Заказы теряются или зависают на одном из этапов, но команда узнает об этом только от клиента, а не от системы. Разрыв между реальным сбоем и обнаружением проблемы - часы или дни.
2. Загрузка растет линейно (100 заказов/мес), но невозможно предсказать, когда ресурсы достигнут предела. Масштабирование происходит реактивно, уже после деградации.
3. С момента открытия B2B API количество жалоб резко выросло, но определить узкое место невозможно без данных о поведении системы под нагрузкой.

Что дает внедрение мониторинга:

- команда переходит от реактивного реагирования на жалобы к проактивному обнаружению проблем;
- появляется возможность измерять эффект от любых изменений в системе (кеш, репликация, масштабирование);
- бизнес получает объективные данные о SLA и может принимать решения на основе метрик, а не ощущений;
- DevOps-инженер получает инструмент для планирования мощностей.

## Выбор подхода к мониторингу

Система состоит из двух типов компонентов с разными характеристиками наблюдаемости.

Для API-сервисов (Shop API, CRM API, MES API) применяется метод RED:

- Rate - количество запросов в секунду;
- Errors - доля ошибочных ответов (HTTP 5xx);
- Duration - время ответа (латентность).

Этот метод ориентирован на пользователя и напрямую отвечает на вопрос "насколько хорошо сервис справляется с нагрузкой прямо сейчас".

Для инфраструктурных компонентов (базы данных, RabbitMQ, EC2-инстансы) применяется метод USE:

- Utilization - насколько занят ресурс (CPU %, Memory %);
- Saturation - насколько ресурс перегружен (очередь соединений, глубина очереди);
- Errors - аппаратные и системные ошибки.

Этот метод позволяет обнаружить проблему на уровне ресурсов до того, как она проявится на уровне сервиса.


| Компонент   | Подход | Обоснование                                                  |
| -------------------- | ------------ | ----------------------------------------------------------------------- |
| Shop API             | RED          | HTTP-сервис, важно качество обслуживания |
| CRM API              | RED          | то же                                                               |
| MES API              | RED          | то же, плюс два типа клиентов                    |
| EC2-инстансы | USE          | ресурсы инфраструктуры                             |
| MES DB, Shop DB      | USE          | ресурсы БД                                                     |
| RabbitMQ             | USE          | ресурс брокера + специфичные метрики     |
| S3                   | USE          | ресурс хранилища                                         |

Четыре золотых сигнала объединяют RED и частично USE в одном подходе. От него отказались в пользу раздельного применения RED и USE. Это дает более четкое разделение между метриками качества обслуживания и метриками ресурсов, упрощает создание отдельных дашбордов для разработчиков и DevOps.

## Метрики и части системы

Ниже приведен разбор метрик по каждому блоку системы. Метрики сгруппированы по компоненту. Нумерация метрик соответствует номерам в списке метрик, приведенных в задании.

### Shop API

Метрика 3: Number of requests (RPS) for internet shop API

Базовая метрика RED. Позволяет видеть пики нагрузки, сравнивать будний и выходной трафик, отслеживать рост нагрузки от B2B API. Падение RPS в рабочее время - сигнал, что сервис не отвечает. Рост RPS сверх нормы - возможная атака или вирусный трафик.

Ярлыки: endpoint (/orders, /files, /catalog), method (GET/POST), status\_code. Без endpoint невозможно понять, какой именно сценарий перегружен.

Метрика 6: Number of requests (RPS) per user for internet shop API

Для B2C (обычные клиенты) эта метрика менее критична чем для MES API. Но полезна для обнаружения скрапинга каталога или автоматических скриптов от одного пользователя. Нужно включить, но с низким приоритетом.

Ярлыки: user\_id (или session\_id для анонимных), api_key.

Метрика 19: Response time (latency) for shop API

Рост latency виден раньше, чем рост ошибок. Сервис начинает тормозить до того, как начнет падать. Особенно важно для эндпоинта загрузки 3d-файлов - там latency выше нормы. Смотрим p50, p95, p99: p50 - медианный пользователь, p99 - худший опыт. Деградация p99 при нормальном p50 - признак проблем с отдельными тяжелыми запросами (загрузка 3D-файла, расчет цены). Среднее значение latency скрывает проблемы - не используем.

Ярлыки: endpoint, percentile.

Метрика 28: Number of HTTP 500 for shop API

Прямой индикатор ошибок. Рост числа ответов 500 означает, что сервис отказывает клиентам. Должен быть настроен алерт при превышении порога error rate.

Ярлыки: endpoint. Так видно, на каком именно сценарии начались ошибки - на создании заказа или на загрузке файла.

Метрика 25: Number of HTTP 200 for shop API

В паре с метрикой 28 (HTTP 500) позволяет считать error rate. Сама по себе мало информативна, но необходима для формулы: error_rate = http_500 / (http_200 + http_500).

Ярлыки: endpoint.

Метрика 9: CPU % for shop API

Единственный инстанс EC2. Если CPU > 80% - сервис начинает деградировать, новые запросы встают в очередь. Для SpringBoot приложения CPU растет при обработке файлов и при сборке мусора.

Ярлыки: instance_id. Пока один инстанс - не критично, но нужно для будущего масштабирования.

Метрика 12: Memory Utilisation for shop API

Java-приложения (SpringBoot) активно используют хип. Рост потребления памяти без освобождения - признак утечки. Достижение лимита приведет к OOM и перезапуску пода.

Ярлыки: instance_id.

Метрика 32: Number of simultaneous sessions

Показывает количество активных клиентских сессий. Помогает понять пиковую конкурентную нагрузку. Полезна для capacity planning - сколько пользователей одновременно работают с магазином и проверки, что rate limiting работает корректно.

Ярлыки: source (web/api). Агрегированное значение достаточно.

Метрики 35 и 38: Kb tranferred (received) for shop API и Kb provided (sent) for shop API

Shop API принимает 3d-файлы. Рост Kb received без роста RPS означает, что клиенты загружают очень большие файлы. Это влияет на latency и S3. Нужно включить метрику 35 (received). Метрика 38 (sent) менее важна - ответы API небольшие.

Ярлык: endpoint (для метрики 35).

Метрика 31: Number of HTTP 500 for shop API

Фактически дубликат метрики 28 в условии задания.

Итоговая таблица для Shop API


| Метрика   | Подход | Включить                      | Ярлыки                   |

DevOps-инженер один. Grafana-дашборды нужно создавать, поддерживать и объяснять команде. Если дашборд содержит много метрик - никто не будет его читать. Алерты на все метрики сразу - это шум, команда начнет их игнорировать.

Лучше разбить введение метрик Shop API на очереди:

1. Метрики выживания - без которых не знаем, работает ли сервис вообще:

* RPS (метрика 3) - есть ли вообще трафик
* HTTP 500 (метрика 28) - есть ли ошибки
* Latency p95 (метрика 19) - отвечает ли быстро

2. Метрики ресурсов. Уже когда базовая видимость есть, добавляем:

* CPU (метрика 9)
* Memory (метрика 12)

3. Метрики для capacity planning. Уже когда система стабильна и нужно планировать рост:

* Simultaneous sessions (метрика 32)
* Kb received (метрика 35)
* RPS per user (метрика 6)

### Messages Queue (RabbitMQ)

Используем подход USE. RabbitMQ - инфраструктурный компонент.

Метрика 1: Number of dead-letter-exchange letters in RabbitMQ

Основная метрика для обнаружения потерянных заказов. Единственная метрика в системе, которая напрямую сигнализирует о потерянном заказе до того, как об этом сообщит клиент. Сообщение попадает в DLX, если потребитель не смог его обработать или превышен TTL. Значение больше нуля означает, что какой-то заказ завис и не будет обработан без ручного вмешательства.

Ярлыки: queue_name (название очереди-источника), reason (expired/rejected/maxlen).

Метрика 2: Number of message in flight in RabbitMQ

Показывает, сколько сообщений взято потребителем, но еще не подтверждено. Рост этого значения означает, что потребитель замедлился или завис. Это ранний признак проблемы с CRM API или MES API.

Ярлыки: queue_name.

### CRM API

Подход - RED

CRM API обслуживает два источника входящего трафика: продавцов через UI и сообщения из Messages Queue от MES API. Рост RPS при стабильном числе активных продавцов - признак аномального потока сообщений из очереди.

Метрика 4: Number of requests (RPS) for CRM API

CRM API обрабатывает запросы от продавцов и события из очереди. Разделение по источнику позволяет изолировать, откуда идет нагрузка - из UI или из Messages Queue (RabbitMQ).

Ярлыки: method, endpoint, status_code, source (ui/queue).

Метрика 20: Response time (latency) for CRM API

Продавцы работают с CRM в реальном времени - подтверждают заказы, меняют статусы. Медленные ответы напрямую снижают скорость прохождения заказа через статус MANUFACTURING_APPROVED.

Ярлыки: endpoint, percentile (p50/p95/p99).

Метрика 29: Number of HTTP 500 for CRM API

Ошибки в CRM API означают, что продавец не может обработать заказ или сообщение из RabbitMQ не было принято. Второй сценарий особенно опасен - необработанное сообщение уйдет в DLX или потеряется.

Ярлыки: endpoint, error_type.

Метрика 26: Number of HTTP 200 for CRM API

Используется совместно с метрикой 29 для расчета error rate.

Ярлыки: endpoint.

Метрика 10: CPU % for CRM API

USE-метрика. SpringBoot на Java - рост CPU при обработке пакетов сообщений из очереди указывает на всплеск входящих событий от MES API.

Ярлыки: instance_id.

Метрика 13: Memory Utilisation for CRM API

Предотвращение OOM на единственном инстансе EC2. Утечки памяти в JVM-приложениях проявляются как монотонный рост без возврата к базовому уровню.

Ярлыки: instance_id.

Метрика 7: Number of requests (RPS) per user for CRM API

Аномальная активность конкретного продавца или некорректного интеграционного клиента. Используется для точечного разбора инцидентов, а не для алертинга.

Ярлыки: user_id.

Метрика 33: Number of simultanious sessions for CRM API

Количество активных продавцов одновременно. Резкий рост без предупреждения - признак нагрузочного теста или аномалии.

Ярлыки: нет.

| ------------------------------------ | ------------ | ----------------------- | ------------------------------------------------- |
| 4 - Number of requests (RPS)         | RED/Rate     | да                    | method, endpoint, status\_code, source (ui/queue) |
| 20 - Response time (latency)         | RED/Duration | да                    | endpoint, percentile (p50/p95/p99)                |
| 29 - Number of HTTP 500              | RED/Errors   | да                    | endpoint, error\_type                             |
| 26 - Number of HTTP 200              | RED/Errors   | да, для error rate | endpoint                                          |
| 10 - CPU %                           | USE          | да                    | instance\_id                                      |

| 33 - Number of simultanious sessions | RED/Rate     | да                    | нет                                            |
| 36 - Kb transferred (received)       | USE          | нет                  | -                                                 |
| 39 - Kb provided (sent)              | USE          | нет                  | -                                                 |

Метрики CRM API вводятся в три очереди:

1. Метрики выживания - без которых не знаем, работает ли сервис:

- RPS (метрика 4) - есть ли трафик от продавцов и из очереди
- HTTP 500 (метрика 29) - есть ли ошибки при обработке заказов
- Latency p95 (метрика 20) - отвечает ли сервис вовремя

2. Метрики ресурсов - когда базовая видимость есть:

- CPU (метрика 10) - не перегружен ли инстанс при пиках из очереди
- Memory (метрика 13) - нет ли утечек памяти в JVM

3. Метрики для capacity planning - когда система стабильна:

- Simultaneous sessions (метрика 33) - пиковая нагрузка от продавцов
- RPS per user (метрика 7) - данные для разбора аномальной активности

Метрики 36 и 39 (Kb transferred) есть в списке задания, но для CRM API они  низкоприоритетны - трафик между CRM API и клиентами небольшой, 3D-файлы  CRM не принимает напрямую.

### MES API

MES API обслуживает два независимых потока: операторов через внутренний UI и B2B-клиентов через публичный endpoint расчета стоимости. Метрики разделяются по источнику через label source, что позволяет изолировать проблему в конкретном потоке.

Метрика 5: Number of requests (RPS)

Базовая линия трафика для двух типов клиентов. Падение RPS от операторов в рабочее время - сигнал недоступности MES. Аномальный рост RPS от B2B - признак отсутствия rate limiting или некорректной интеграции на стороне партнера.

Ярлыки: method, endpoint, status_code, source (internal/external).

Метрика 21: Response time (latency)

Напрямую соответствует жалобам операторов на медленную загрузку дашборда. После внедрения Redis-кеша эта метрика станет основным доказательством эффекта для бизнеса. Нужно смотреть p95 и p99, среднее значение скрывает проблемы.

Ярлыки: endpoint, percentile (p50/p95/p99).

Метрика 30: Number of HTTP 500

Ошибки MES API означают либо недоступность для операторов, либо отказ B2B-клиенту в расчете стоимости. Оба сценария напрямую влияют на выручку. Наиболее критичная метрика по бизнес-последствиям.

Ярлыки: endpoint.

Метрика 27: Number of HTTP 200

Используется совместно с метрикой 30 для расчета
error rate = HTTP500 / (HTTP500 + HTTP200). Сам по себе
рост HTTP 200 не информативен, но без него процент ошибок
не посчитать.

Ярлыки: endpoint.

Метрика 11: CPU % for MES API
Расчет стоимости - CPU-затратная операция длиной до 30 минут. Нужно понимать, как долгие вычисления влияют на способность MES API обслуживать других клиентов параллельно. Рост CPU без роста RPS указывает на тяжелый расчет в процессе.

Ярлыки: instance_id.

Метрика 14: Memory Utilization
Обработка сложных 3D-моделей требует загрузки геометрии в память. При нехватке памяти инстанс уходит в swap, что кратно увеличивает время расчета и деградирует весь сервис.

Ярлыки: instance_id.

Метрика 8: Number of requests per user
B2B-клиенты, генерирующие избыточный трафик, исчерпывают ресурсы системы в ущерб остальным партнерам и операторам. Метрика дает данные для настройки индивидуальных лимитов по api_key и для обнаружения некорректных интеграций.

Ярлыки: api_key, endpoint.

Метрика 34: Number of simultaneous sessions
Количество операторов, одновременно работающих с MES, коррелирует с нагрузкой на MES DB. Позволяет планировать размер connection pool и прогнозировать пиковую нагрузку.

Ярлыки: нет.


| Метрика | Описание      | Подход | Включить        | Ярлыки                          |
| -------------- | --------------------- | ------------ | ----------------------- | ------------------------------------- |
| 5              | RPS                   | RED/Rate     | да                    | method, endpoint, status_code, source |
| 21             | Latency               | RED/Duration | да                    | endpoint, percentile (p50/p95/p99)    |
| 30             | HTTP 500              | RED/Errors   | да                    | endpoint, error_type                  |
| 27             | HTTP 200              | RED/Errors   | да, для error rate | endpoint                              |
| 11             | CPU %                 | USE          | да                    | instance_id                           |
| 14             | Memory                | USE          | да                    | instance_id                           |
| 8              | RPS per user          | RED/Rate     | да                    | api_key, endpoint                     |
| 34             | Simultaneous sessions | RED/Rate     | да                    | -                                     |

Метрики MES API разбиты на три очереди внедрения.

1. Метрики выживания - без которых не знаем, работает ли сервис:

- RPS (метрика 5) - есть ли трафик от операторов и B2B-клиентов
- HTTP 500 (метрика 30) - есть ли ошибки, влияющие на заказы
- Latency p95 (метрика 21) - отвечает ли сервис в приемлемое время
- Длительность расчета стоимости (вне списка) - не завис ли расчет

2. Метрики ресурсов - когда базовая видимость есть:

- CPU (метрика 11) - не перегружен ли инстанс расчетами
- Memory (метрика 14) - не уходит ли инстанс в swap на тяжелых моделях

3. Метрики для capacity planning - когда система стабильна:

- RPS per user (метрика 8) - кто из B2B-клиентов генерирует избыточный трафик, данные для настройки индивидуальных лимитов
- Simultaneous sessions (метрика 34) - пиковая нагрузка от операторов, данные для планирования connection pool MES DB

#### Shop DB

Подход - USE

Shop DB - единственное хранилище данных о заказах и клиентах для Shop API и CRM API одновременно. Два сервиса конкурируют за один пул соединений. При росте B2B-трафика через CRM API эта конкуренция усиливается.

Метрика 17: Number of connections for shop db instance

Критичная метрика для единственного инстанса без реплики. HikariCP в SpringBoot держит пул соединений - при исчерпании пула новые запросы от Shop API и CRM API встают в очередь или падают с ошибкой. Это наиболее частая причина каскадного сбоя при росте нагрузки.
Ярлыки: db_instance, state (active/idle/waiting).

Метрика 15: Memory Utilisation for shop db instance

PostgreSQL использует shared_buffers и page cache для ускорения запросов. При нехватке памяти база начинает читать с диска, что кратно увеличивает время выполнения запросов.
Ярлыки: db_instance.

Метрика 23: Size of shop db instance

Shop DB хранит все данные о заказах и клиентах. При линейном росте заказов база растет прогнозируемо. Нужно планировать дисковое пространство и стоимость managed-сервиса заранее.
Ярлыки: db\_instance.

| ----------------------------- | --------------- | ---------------- | ----------------------------------------- |
| 17 - Number of connections    | USE/Saturation  | да             | db\_instance, state (active/idle/waiting) |
| 15 - Memory Utilisation       | USE/Utilization | да             | db\_instance                              |
| 23 - Size of shop db instance | USE/Utilization | да             | db\_instance                              |

1. Метрики выживания:

- Connections (метрика 17) - не исчерпан ли пул соединений

2. Метрики ресурсов:

- Memory (метрика 15) - достаточно ли памяти для page cache

3. Метрики для capacity planning:

- Size (метрика 23) - когда закончится место на диске

#### MES DB

Подход - USE

MES DB обслуживает только MES API, но под двумя типами нагрузки одновременно: операторы читают дашборд заказов, MES API пишет изменения статусов. Именно конкуренция чтения и записи на одном инстансе является корневой причиной медленной загрузки дашборда.

Метрика 18: Number of connections for MES db instance

Каждый оператор при открытии дашборда выполняет тяжелый запрос. При нехватке соединений запросы операторов встают в очередь - это и есть то, что они называют "долгой загрузкой страницы". После внедрения Redis-кеша эта метрика покажет снижение нагрузки.
Ярлыки: db_instance, state (active/idle/waiting).

Метрика 16: Memory Utilisation for MES db instance

PostgreSQL кеширует горячие данные в page cache. Список заказов по статусам - это горячие данные, которые должны оставаться в памяти. При нехватке памяти каждый запрос оператора идет на диск.
Ярлыки: db_instance.

Метрика 24: Size of MES db instance

MES DB хранит историю всех производственных операций. При росте заказов на 100 в месяц размер базы растет предсказуемо. Нужно для планирования дискового пространства managed-сервиса.
Ярлыки: db_instance.


| Метрика               | Подход    | Включить | Ярлыки                              |
| ---------------------------- | --------------- | ---------------- | ----------------------------------------- |
| 18 - Number of connections   | USE/Saturation  | да             | db\_instance, state (active/idle/waiting) |
| 16 - Memory Utilisation      | USE/Utilization | да             | db\_instance                              |
| 24 - Size of MES db instance | USE/Utilization | да             | db\_instance                              |

Метрики MES DB вводятся по очереди:

1. Метрики выживания:

- Connections (метрика 18) - не исчерпан ли пул при пике операторов

2. Метрики ресурсов:

- Memory (метрика 16) - держатся ли горячие данные в page cache

3. Метрики для capacity planning:

- Size (метрика 24) - прогноз роста при линейном росте заказов

#### 3d files storage (S3)

Подход - USE

S3 используют три сервиса: Shop API загружает 3D-файлы от клиентов, MES API читает их для расчета стоимости, CRM API обращается к ним при работе с заказами. Размер хранилища растет с каждым новым
заказом и не уменьшается - файлы не удаляются автоматически.

Метрика 22: Size of S3 storage

Каждый заказ добавляет минимум один 3D-файл. Сложные модели занимают значительный объем. Без контроля размера превышение квоты или бюджета на хранение станет неожиданностью.
Ярлыки: bucket_name.

Очередности ввода метрик нет.

## План действий

Все задачи выполняет один DevOps-инженер. Порядок соответствует очередности фаз внедрения метрик.

Этап 1: инфраструктура сбора метрик

- Развернуть инстанс Prometheus на отдельном EC2 в Yandex Cloud.
- Развернуть Grafana, подключить Prometheus как источник данных.
- Развернуть AlertManager, настроить канал уведомлений в мессенджер
  команды (Slack или Telegram).
- Установить node_exporter на каждый EC2-инстанс: Shop API, CRM API, MES API. Это дает CPU и Memory без изменений в коде.
- Установить postgres_exporter для Shop DB и MES DB. Managed PostgreSQL в Yandex Cloud поддерживает внешние экспортеры.
- Установить rabbitmq_exporter для Messages Queue. Дает метрики глубины очереди, in-flight и DLX.
- Настроить S3-метрики через Yandex Cloud Monitoring API или CloudWatch-совместимый endpoint.

Этап 2: инструментация сервисов

- Добавить Micrometer в Shop API и CRM API (SpringBoot). Spring Boot Actuator уже включен в стандартный стек - достаточно добавить зависимость micrometer-registry-prometheus и открыть endpoint /actuator/prometheus.
- Добавить OpenTelemetry metrics SDK в MES API (C#). Использовать пакет OpenTelemetry.Exporter.Prometheus.AspNetCore. Задача для единственного C#-разработчика, тимлид участвует в ревью.

Этап 3: дашборды и алерты

- Создать дашборд для каждого компонента: Shop API, CRM API, MES API, RabbitMQ, Shop DB, MES DB, S3.
- Настроить алерты фазы 1 в AlertManager:
  - DLX > 0 - немедленное уведомление
  - HTTP 500 rate > 5% за 5 минут - уведомление DevOps
  - Latency p95 > порогового значения - уведомление DevOps
  - Connections > 80% от лимита пула - уведомление DevOps
- Зафиксировать baseline метрик после двух недель наблюдения. Baseline используется для настройки пороговых значений алертов фазы 2 и 3.

Этап 4: метрики фазы 2 и 3

- Добавить детальные labels к существующим метрикам после стабилизации сбора данных.
- Настроить алерты для метрик ресурсов: CPU > 80%, Memory > 85%.
- Подключить capacity planning дашборды: рост S3, рост БД, прогноз исчерпания ресурсов.

#### Дополнительное задание: показатели насыщенности

Насыщенность - степень заполненности ресурса. В отличие от утилизации, насыщенность показывает, когда ресурс начинает работать на пределе и следующий всплеск нагрузки приведет к отказу. Пороговые значения установлены ниже максимума - это дает время на реакцию до того, как система начнет отказывать.

Пул соединений Shop DB и MES DB
Пороговое значение: 80% от максимального числа соединений.

При 80% загрузки пула новые запросы начинают вставать в очередь ожидания. При 95% HikariCP начинает
выбрасывать исключения. Разрыв между 80% и отказом дает около 10-15 минут на реакцию при линейном росте нагрузки.
Конкретное значение зависит от настройки max_connections в Managed PostgreSQL на Yandex Cloud.

Действия при превышении:

- AlertManager отправляет уведомление DevOps-инженеру.
- DevOps проверяет, какой сервис создает избыточные соединения.
- Если причина в пике нагрузки - рассмотреть добавление
  PgBouncer как connection pooler перед БД.
- Если причина в утечке соединений - завести тикет на разработчика
  соответствующего сервиса с приоритетом high.

CPU на EC2-инстансах
Пороговое значение: 80% в течение 5 минут.

Кратковременные пики CPU до 100% допустимы, например при старте JVM или во время GC. Устойчивые 80% в течение 5 минут означают, что инстанс обрабатывает
нагрузку на пределе и следующий запрос может получить таймаут.  Для MES API особенно важно - расчет стоимости CPU-интенсивен, и длительное вычисление может заблокировать обработку других запросов.

Действия при превышении:

- AlertManager уведомляет DevOps-инженера.
- Для MES API: проверить, идет ли тяжелый расчет стоимости.
  Если да - ожидаемое поведение, мониторить до завершения.
- Для Shop API и CRM API: аномалия, завести тикет на исследование.
- Если CPU устойчиво выше порога более часа - запросить
  увеличение типа инстанса EC2 через Yandex Cloud консоль.

Memory на EC2-инстансах
Пороговое значение: 85% от доступной памяти.

JVM (SpringBoot) и .NET (C#) требуют свободной памяти для работы сборщика мусора. При заполненности выше 85%
GC начинает работать агрессивно, что увеличивает latency. При 95% возникает риск OOM Kill - операционная система
принудительно завершит процесс.

Действия при превышении:

- AlertManager уведомляет DevOps-инженера.
- Проверить график потребления памяти: монотонный рост без
  возврата к базовому уровню - признак утечки памяти.
  Завести тикет разработчику с приоритетом high.
- Если рост памяти коррелирует с ростом трафика - это
  ожидаемое поведение, рассмотреть увеличение RAM на инстансе.

RabbitMQ: глубина очереди
Пороговое значение: рост очереди в течение 10 минут без уменьшения.

Очередь должна расти и уменьшаться в рабочем ритме. Если очередь только растет 10 минут подряд - consumer недоступен
или не справляется с нагрузкой. Именно 10 минут выбраны потому, что короткие всплески (1-2 минуты) могут быть нормой при пике
входящих заказов.

Действия при превышении:

- AlertManager уведомляет DevOps-инженера.
- Проверить статус consumer-сервиса (CRM API или MES API).
- Если сервис недоступен - перезапустить инстанс EC2.
- Если сервис работает, но не справляется - зафиксировать
  объем накопившейся очереди и завести тикет на горизонтальное
  масштабирование consumer.

RabbitMQ: Dead Letter Exchange
Пороговое значение: любое значение больше нуля.

Появление сообщения в DLX означает потерянный заказ. Нет допустимого ненулевого значения - каждое сообщение
в DLX требует ручного разбора.

Действия при превышении:

- AlertManager отправляет немедленное уведомление DevOps-инженеру
  и тимлиду одновременно.
- Тимлид вручную проверяет сообщение в dead-letter-queue:
  определяет order_id, статус заказа, причину попадания в DLX.
- Принимается решение о повторной обработке или ручном
  переводе заказа в корректный статус через CRM.
- Заводится тикет на устранение причины с приоритетом highest.

S3 и размер БД
Пороговое значение: 80% от выделенного объема или планового бюджета.

Обоснование: Managed PostgreSQL на Yandex Cloud требует ручного увеличения диска. Это не мгновенная операция.
80% дают достаточно времени для планового расширения без риска аварийной остановки сервиса.

Действия при превышении:

- AlertManager уведомляет DevOps-инженера.
- DevOps запрашивает увеличение дискового пространства
  через Yandex Cloud консоль.
- Продакт-менеджер получает уведомление о росте расходов
  на инфраструктуру для планирования бюджета.
- Для S3: рассмотреть политику архивирования старых 3D-файлов
  в более дешевый класс хранения.
